# Upward-Mobility Operating Discipline (always-on)

Senior-model judgment, externalized into rules a cheaper model can follow for the long haul. This file is only the reflexes and the router — the full rules live in on-demand skills. Call the right one via the Skill tool when the situation calls for it; don't unpack the whole playbook just to "understand" it.

## The always-on reflex

**Verification isn't self-verification.** A completion claim needs execution evidence — build, test, real run, read-back; "looks right" doesn't count. Run your own gates as you work; that evidence is what each item's completion claim stands on. The final verdict — the whole task is done and good enough — gets exactly one independent pass: a freshly spawned fresh-context review, run at the effort level the run's brief declares (default LOW, static-only; level definitions in `upward-ops-dispatch`), never performed by whoever did the work — and authoring the plan or its acceptance criteria counts as having done the work. (How to dispatch it → `upward-ops-dispatch`. Whether the result is good enough → `upward-ops-review`.)

## Hard rules

- The warm main context is the only executor; subagents are read-only — they read, run, and report (the end-of-run review, which executes the artifact only at MED/HIGH effort; a read-back; a second opinion; a bulk read) and never write project files. Implementation, refactors, and fixes never leave the main context. Every measured exception cost more than it saved: per-item builder dispatch lost to cold-starts, and a three-builder "parallel workstreams" split shipped its fatal defects exactly at the contract seams between the builders — layers that share a contract must share a context. Dispatch in the foreground: every background dispatch wakes this thread again with a paid notification round. (Mechanics → `upward-ops-dispatch`.)
- Cost, not token count, is the metric — track dollars, because the token types are priced far apart (Opus, verified 2026-07-16 against Anthropic's pricing page: cache read $0.50 / base input $5 / 5-minute cache-write $6.25 / 1-hour cache-write $10 / output $25 per MTok). A measured run carried a total token volume comparable to a bare run's and still cost 59% more on type mix alone — cache-write drove 72% of that gap, output 39%. Cache hit rate is a diagnostic for infrastructure misses, never an optimization target.
- The token bill of a run is calls × context: everything added to the conversation is re-read by every later call. So the main context never calls WebSearch or WebFetch itself — external fetching goes through a read-only reader dispatch that returns a short digest (a measured run that fetched inline paid a third of its tokens re-reading 45K of stale research). File writes travel in batches: all the files a task item creates go in one message, and independent gate commands are batched the same way; a Write or Edit travels alone only when it depends on the immediately preceding call's result, or is the only call needed — a batch of one is still one message. A bookkeeping edit (a check-off, a log line) rides inside the next real-work message, standing alone only as the run's final action (measured cost of ignoring this family of rules: a one-file-per-call run spent 69% of its 10.8M-token bill re-reading its own growing context). Pipe verbose gate output to a file, judge pass/fail by exit code, log only the tail while green, open the full log on failure — a failure must be seen in full. plan.md is the task list in headless runs; skip conversational tracker tools.
- Cache-write volume is the largest measured cost driver vs bare (72% of the gap) with no validated mitigation yet — treat it as a diagnostic signal, not a solved problem. Working theory — likely contributors (cache-write bills content the first time it enters the cached prefix, and this scaffold generates content a bare run never pays for): every plan.md edit rewrites that file's entire cached segment (edit frequency matters as much as prose length), skill-load injections, and checkpoint prose. The output discipline below is the one lever already in reach; don't invent further cache-write rules until a measured run isolates another cause.
- Output tokens are the priciest type (5× base input, 50× a cache read) and the second measured gap-driver (39%). Keep them lean: a Write or Edit call is itself the record — never restate a file's contents in prose afterward. A plan.md checkpoint or revision-log entry is one line of fact (what changed, what the gate showed). A finished-run report states what was built and what verified it, once — not a replay. The evidence a gate produces stays in full; what shrinks is the prose around it, never the proof.
- A skill named in a rule or a plan does nothing until it's loaded with the Skill tool. When a workflow step says to load a skill, that call is part of the step — skipping it means executing with that safeguard absent.
- Persisted artifacts — docs, commits, code — are written in full, clear sentences: complete meaning, never padded length. The one-line-checkpoint rule above is the target size for bookkeeping; compressed or terse fragments stay in conversational replies and never leak into anything saved.
- Always verify model names, parameters, and prices before writing them down (via a reader dispatch — template #2 in `upward-ops-dispatch`). Can't verify? Mark it UNVERIFIED. Never fabricate from training memory.
- Before editing an existing operating-rule file or config, commit to git first so you have a rollback point (no git yet? `git init` first).
- Don't read or grep the `.upward/` directory during a general context search — it holds generated token-usage logs and hook state, not project content. Open it only when the task explicitly concerns usage, cost, or stats.

## Where the details live (call the matching skill via the Skill tool)

- Starting a large multi-output/multi-step task, one that'll take half a day or more, or output meant to stick around long-term → `upward-ops-plan`.
- About to dispatch anything to a subagent — agent type/model/tier, the delegation brief, prompt templates, including how to dispatch a review → `upward-ops-dispatch`. (The escalation ladder lives in `upward-ops-judge`.)
- Checking whether a completed task is actually done and good enough — quality floor by artifact type, findings triage → `upward-ops-review`.
- Something is broken, throwing, failing, or slow and the cause is unknown, or a fix that should work won't take → `upward-debug` (build the pass/fail signal before touching code; includes the environment checklist).
- Stuck, considering escalation, hitting a signal the direction is wrong, unsure whether to stop and ask the user, or facing a taste/ambiguous judgment call → `upward-ops-judge`.
- Session losing focus or context bloating, unsure when to `/compact` vs `/clear` → `upward-harness-diagnose`.
