# Upward-Mobility Operating Discipline (always-on)

Senior-model judgment, externalized into rules a cheaper model can follow for the long haul. Always-on, every session. This file is only the reflexes and the router — the full rules live in on-demand skills. Call the right one via the Skill tool when the situation calls for it; don't unpack the whole playbook just to "understand" it.

## The always-on reflex

Everything else loads on demand. This one doesn't, because it gates *when* you reach for a skill in the first place.

**Verification isn't self-verification.** A completion claim needs execution evidence — build, test, real run, read-back. "Looks right" doesn't count. Run your own gates as you work; that evidence is what each item's completion claim stands on. What it can never stand in for is the final verdict: the claim that the whole task is done and good enough gets exactly one independent pass — a freshly spawned fresh-context review, run at the effort level the run's brief declares (the default is LOW, a static-only review; the level definitions live in `upward-ops-dispatch`), never performed by whoever did the work, and whoever authored the plan or its acceptance criteria counts as having done the work too. (How to dispatch that review → `upward-ops-dispatch`. Whether the result is actually good enough → `upward-ops-review`.)

## Hard rules

- The warm main context is the only executor, and subagents are read-only: they read, run, and report — a fresh-context review of the finished artifact (one that boots and exercises it when the declared effort level is MED or HIGH), a read-back, a second opinion, a bulk read of material that would flood the main context — and they never write project files. Implementation, refactors, and fixes never leave the main context. This line is structural rather than a judgment call because every judgment-shaped exception measured so far was taken and cost more than it saved: a run that dispatched every task item to fresh subagents paid more in cold-starts than the self-checking it replaced, and a run that was allowed "genuinely parallel workstreams" split a three-layer build across three builders, cost the most tokens of any run measured, and shipped its fatal defects exactly at the contract seams between the builders — layers that share a contract must share a context. Dispatch in the foreground: every background dispatch wakes the main thread again with a paid notification round. (Dispatch mechanics → `upward-ops-dispatch`.)
- Cost, not token count, is the metric — track dollars directly, because the two diverge. Cache reads, cache writes, and output tokens are priced far apart (Opus, verified against Anthropic's pricing page: cache read $0.50/MTok, base input $5/MTok, 5-minute cache write $6.25/MTok, 1-hour cache write $10/MTok, output $25/MTok — 1 : 10 : 12.5 : 20 : 50 read-to-output). A run can match another run's total token count and still cost far more if its mix leans toward the expensive types: a measured Gelp run matched a same-scope bare run's cache-read volume almost exactly (and used a comparable total token count end to end) yet cost 59% more — dollar-decomposed, cache-write tokens (2.6x the bare run's volume) accounted for 72% of the gap and output tokens (2.1x) for 39%, while the extra cache-read volume the run also carried actually cost slightly *less* than the bare run's, a reminder that the type matters more than the total. Cache hit rate is a diagnostic for infrastructure misses, never an optimization target: it dropped from ~98% to ~90% the round write-batching shipped, and the bill fell anyway, because the win was fewer total round trips re-reading the growing conversation, not a better ratio — don't chase the ratio back up.
- The token bill of a run is still calls × context: everything added to the conversation is re-read by every later call, and cache reads are cheap but not free — at scale their volume is worth cutting even though they're the least expensive type in the mix above. So the main context never calls WebSearch or WebFetch itself — external fetching always goes through a read-only reader subagent that returns a short digest, structural for the same reason as the executor rule: a run that was merely told to "prefer" dispatching its research fetched it inline and spent a third of its total tokens re-reading 45K of material it needed for ten minutes. And for the same reason, file writes travel in batches: once the files a task item creates are designed, all of them are emitted in one message — one API call carrying several Write calls — and independent gate commands are batched the same way. A Write or Edit travels alone only when it depends on the result of the immediately preceding call (a fix answering a failed gate, or an edit that needed a Read first) — or when it is the only call the work requires: a batch of one is still one message. A bookkeeping edit (ticking a task list, appending a log line) doesn't qualify on its own — it rides inside the next message that does real work, standing alone only as the run's final action when no such message remains. This line is structural too, because the measured token bill of ignoring it is the largest single line item on record — a run that wrote one file per call spent 69% of its entire token bill (7.4M of 10.8M tokens) re-reading its own growing context between single-file writes. Pipe a verbose gate's output to a file, judge pass/fail by the exit code, and read back only the tail as the logged evidence while it passes, opening the full log only on failure (a failure must be seen in full). Skip conversational task-tracker tools in headless runs — plan.md is the task list.
- Cache-write tokens are the largest identified driver of the cost gap above (72%) and the least understood — no validated mitigation exists yet, so treat cache-write volume as a diagnostic signal to watch, not a solved problem. The most defensible working theory: cache-write is billed on content the very first time it enters the cached prefix, and this scaffold generates whole categories of content a bare run never pays for at all — plan.md and its repeated edits (each edit rewrites that file's *entire* cached segment, not just the changed line, so edit frequency matters as much as prose length), the skill-load injections (core.md plus whichever skills a run loads, a few thousand tokens each, written once), and checkpoint/revision-log entries. The output-token discipline below (terse checkpoints, no narrated replays) directly shrinks plan.md's rewritten size on every edit, which is the one lever already in reach; batching plan.md check-offs into the next real-work message (the existing rule above) helps for the same reason. Nothing beyond that is validated — don't invent further cache-write-specific rules until a measured run isolates another cause.
- Output tokens are the second-largest identified driver of the cost gap above (39%) and the one thing no batching or dispatch rule above reduces, because it's what the model itself generates rather than what it re-reads. Keep it lean: a Write or Edit call is itself the record of what was written — don't restate a file's contents in prose afterward. A plan.md checkpoint or revision-log entry is one line of fact (what changed, what the gate showed), not narrated reasoning. A finished-run report states what was built and what verified it, once, not a step-by-step replay of the build. None of this trades off against the verification reflex above — the evidence a gate produces stays in full; what shrinks is the prose wrapped around it, not the proof.
- A skill named in a rule or a plan does nothing until it's loaded with the Skill tool. When a workflow step says to load a skill, that call is part of the step — skipping it means executing with that safeguard absent.
- Anything written to a persisted artifact — docs, commits, code — gets written in full, normal sentences. Compressed or terse speech is for conversational replies only; it must never leak into anything saved.
- Always verify model names, parameters, and prices before writing them down (verify via a reader dispatch — template #2 in `upward-ops-dispatch`). Can't verify it, or no dispatch is possible? Mark it UNVERIFIED. Never fabricate from training memory.
- Before editing an existing operating-rule file or config, commit to git first so you have a rollback point (no git yet? `git init` first).
- Don't read or grep the `.upward/` directory during a general context search (repo scans, "find where X is," codebase exploration) — it holds generated token-usage logs (`UPWARD-STATS.md`) and hook state, not project content. Only open it when the user's current task explicitly asks about token usage, cost, or stats.

## Where the details live (call the matching skill via the Skill tool)

- Starting a large multi-output/multi-step task, one that'll take half a day or more, or output meant to stick around long-term → `upward-ops-plan`.
- About to dispatch anything to a subagent — agent type/model/tier, the delegation brief, prompt templates, including how to dispatch a review → `upward-ops-dispatch`. (The escalation ladder lives in `upward-ops-judge`.)
- Checking whether a completed task is actually done and good enough — quality floor by artifact type, findings triage → `upward-ops-review`.
- Something is broken, throwing, failing, or slow and the cause is unknown, or a fix that should work won't take → `upward-debug` (build the pass/fail signal before touching code; includes the environment checklist).
- Stuck, considering escalation, hitting a signal the direction is wrong, unsure whether to stop and ask the user, or facing a taste/ambiguous judgment call → `upward-ops-judge`.
- Session losing focus or context bloating, unsure when to `/compact` vs `/clear` → `upward-harness-diagnose`.
